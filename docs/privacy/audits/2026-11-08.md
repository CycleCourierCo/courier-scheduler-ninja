# GDPR audit, 2026-11-08

Scope: live database (tables, columns, buckets, policies, cron jobs, auth users), edge functions, browser code, index.html and package.json, and the latest Lovable security scan results (dated 2026-10-24, out of date).
First audit: there was no earlier audit, no data map and no personal-data-registry.ts. No application code or database was changed. This audit only created `docs/privacy/data-map.md` and this report.

This is a working review against UK GDPR, DPA 2018, PECR and the Data (Use and Access) Act 2025. It is not legal advice.

## Top five fixes (in priority order)

1. **Add retention purge jobs** (one migration plus cron):
   - `tracking_postcode_attempts`: delete rows older than 30 days (12,604 IP rows since 2026-06-15).
   - `webhook_delivery_logs`: delete after 90 days, or remove `payload` and `response_body` after 30 days (21,355 rows since 2025-11-17, each with full order addresses).
   - `api_request_logs`: 90 days (80,663 rows).
   - `email_delivery_events`: 12 months; remove `payload` after 90 days (195,752 rows).
   - `fleet_eta_links`: remove `sent_to_phone` and `sent_to_email` 30 days after `expires_at`.
   - `mechanic_timeslips` clock-in/out GPS, and photos in `mechanic-clock-photos`: delete after the agreed period (suggest 12 months). Delete storage files alongside their rows.
   - `cs_messages`, `cs_conversations`, `cs-attachments`: 24 months after the last message, unless linked to a claim.
   - Periods are suggestions; the user confirms them before the migration is written.
2. **Build privacy-request tooling**:
   - A `privacy_requests` table with received, verified, due and closed dates, visible to admins with overdue items flagged.
   - `supabase/functions/_shared/personal-data-registry.ts` listing every table in the data map, its match column (user_id, email, phone, or a path in the order snapshot JSON) and its erasure action.
   - An admin-only `privacy-export` function (JSON) and a `privacy-erase` function that anonymises order snapshots, deletes contacts, CS records and files, removes the sign-in, and lists external systems to action (Shipday, QuickBooks, Shopify, Resend, SendZen).
   - Change `delete-user` to call the erase routine rather than deleting only the sign-in.
3. **Rewrite the privacy notice (v2.0) and add a complaints route**:
   - Name the controller (Cycorco Ltd, company no. 16220087, registered office) and the ICO registration number.
   - List each purpose with its lawful basis, the processors and transfers in the data map, retention periods and rights, including complaining to the ICO.
   - Add a "Privacy complaint" form that logs to `privacy_requests` (type = complaint) and sends an acknowledgement.
   - Add a version and date, and remove the "marketing" purpose unless marketing is actually sent.
   - Link it from the footer of every public page, including the availability, repair-offer, inspection-approval, NI partner and ETA pages and the sign-up form.
   - Publish a separate staff and driver privacy notice covering GPS, clock-in photos, licence checks, pay and reviews.
4. **Fix tracking before consent** (`src/lib/posthog.ts`, `src/main.tsx`, `src/contexts/AuthContext.tsx`, `index.html`):
   - Stop sending email to PostHog and Sentry (use the user id only); set `sendDefaultPii: false`.
   - Start PostHog with `persistence: "memory"` (no cookies) until the visitor has seen a notice, or make it opt-in.
   - Add a small analytics notice with Accept / Reject buttons of equal weight and a "Cookie settings" link in the footer, and store the choice with the notice version.
   - Keep Sentry replays masked (the default) and consider capturing replays only when an error happens.
   - Self-host the Overpass fonts so visitors' IP addresses are not sent to Google.
5. **Add marketing suppression to announcements** (`send-announcement-batch`, `process-scheduled-announcements`, `send-announcement-whatsapp`):
   - Add a `marketing_opt_outs` table checked before every send.
   - Add an unsubscribe link to email announcements (emailLayout already supports extra footer links) and a "reply STOP" line to WhatsApp ones.
   - Tag each announcement as service or marketing; marketing only goes to people with consent or a recorded soft opt-in.

## Drift list

The data map and registry did not exist, so everything found is undocumented. See `docs/privacy/data-map.md` for the full list. Main gaps:

- Data that exists but was not documented: everything in the data map, about 60 tables and 12 buckets with personal data, notably `orders` snapshots, `contacts`, `cs_*`, `email_delivery_events`, `webhook_delivery_logs`, `tracking_postcode_attempts` (IP), `driver_positions`, `fleet_position_history`, `mechanic_timeslips` (GPS and photos), `profiles` licence and pay fields, `review_cycles`, and the buckets `driver-licences`, `mechanic-clock-photos`, `cs-attachments`, `delivery-proofs`, `inspection-reports` and `claim-evidence`.
- Documented things that no longer exist: none (there was no documentation).
- Privacy notice against reality: the notice says "IP address... location" (true), but does not mention WhatsApp/SMS messaging, GPS tracking, partner apps, photos, signatures or any of the processors.
- Secrets with no code use: `OPTIMOROUTE_API_KEY`, `TWOCHAT_API_KEY`, `TWOCHAT_FROM_NUMBER`. Delete them if those services are finished.
- `supabase/functions/_shared/personal-data-registry.ts` does not exist (fix 2).
